# 2.0.55

## 修复：米家设备较多时同步反复失败（aggregate_capacity / -23）
- 现象：米家云端设备列表分 8 页返回，聚合后的 JSON 约 **720KB**，超过旧的 512KB
  缓冲，日志出现：
  `MIJIA device_list error=aggregate_capacity bytes=720618 cap=524288`
  随后 `MIJIA devices end result=-23`，下一轮又从第 1 页开始重拉，既拖慢同步也造成
  实体池反复重建。
- 修复：设备列表聚合缓冲从 512KB 提高到 **2MB**，给设备数量继续增长留余量。
- 影响范围：只影响米家云端设备列表的内存缓冲，不改变实体池上限（仍为 8192）；
  缓冲按需分配，设备少时不会额外占用。

## 修复：米家设备名响应超过 64KB 导致 names=0
- 现象：设备名查询响应达到 65535B，旧的 64KB 栈缓冲写满，HTTP 返回 `-23`，
  日志显示 `MIJIA device_names end names=0`。
- 修复：改为 **256KB 堆缓冲**，并在所有返回路径释放。

## 修复：传感器卡片读数不显示单位
- 现象：传感器卡片的大字读数只有数值（如 `23.4`），没有单位；状态栏传感器槽位原本
  已按 `unit_of_measurement` 拼单位，但卡片走的是另一条渲染路径，`nx5_entity_state_t`
  里没有单位字段。
- 修复：实体状态增加 `unit` 字段，由 HA 实体/米家实体同步填充；传感器卡片的大字读数和
  详情页状态行按实体单位拼接（`23.4°C`、`45%`、`12μg/m³` 等）。非数值/二进制传感器
  不拼单位，避免出现 `on°C`。
- 状态栏原有行为不变（已经带单位）。

## 修复：「分时段亮度」首次打开报“设备响应不是有效 JSON”
- 现象：设备上还没有 `brightness_schedule.json` 时，打开设置页「启用分时段亮度」报
  `读取失败：设备响应不是有效 JSON (HTTP 200)`。
- 原因：GET 无文件时返回的默认 JSON 长度写成 26，实际字符串 27 字节，**收尾的 `}` 被截断**，
  前端解析失败。只要保存过一次（文件已存在）就恢复正常，所以该问题只在首次使用时出现。
- 修复：长度改为 27（2.0.55）。保存路径（POST）不受影响，已复测写盘/回读正常。

## 说明
- 本次只改米家云端列表/设备名两条大响应路径，不涉及 HA 实体筛选规则、显示与开机链。
- 若现场同时出现 Wi-Fi 反复 `assoc failed x3 -> reconfigure`，那是无线关联/AP 侧问题，
  与本修复无关；有线 eth0 正常时 HA/米家云端仍可工作。
